## 8.1 Diffie-Hellman key exchange

Public group (p, g). Alice picks secret `a`, sends `A = g^a mod p`; Bob picks `b`, sends `B = g^b mod p`. Each computes the same
secret because `B^a = g^(ab) = A^b`. Textbook run, p = 23, g = 5: a = 6 → A = 8; b = 15 → B = 19; both compute **2**. The
same code runs over the standardised **RFC 7919 groups** (ffdhe2048/3072/4096, extracted from OpenSSL; the tests verify
that `p` and `(p−1)/2` are both prime and that `g = 2` lies in the prime-order subgroup). Practical rules built in: **validate
the peer's public value** (reject 0, 1, p−1 and anything outside the subgroup) and **never use the raw secret as a key**; it
goes through HKDF.

**Why the group must be large.** An eavesdropper sees `A` and wants `a`, the discrete logarithm. Baby-step giant-step does
that in ~√(group order): on a 40-bit prime it recovered the exponent in **1.7 seconds** (about 2^20 steps). A 2,048-bit group
needs ~2^1023 steps for the same generic attack.

## 8.2 MITM on unauthenticated DH, and the fix

```
no attacker           : Alice and Bob keys equal: True
VULNERABLE + Mallory  : Alice/Bob keys differ: True | Mallory shares a key with each side: True | neither side noticed anything
signed, no attacker   : keys equal: True
signed + Mallory      : ABORTED -> Alice: Bob's signature does not match the values I exchanged; aborting
```

Vulnerable: Mallory swaps each public value for her own, so Alice's secret is `g^(a·mb)` and Bob's is `g^(b·ma)`, both
computable by Mallory. DH gives a *shared secret*, not an *identity*. **Fix (Station-to-Station style):** each side signs the
pair of public values with a long-term identity key the other already trusts: `A → ; B, Sig_B(B|A) → ; Sig_A(A|B)`.
Mallory cannot forge a signature over her substituted values, so the first check fails and the exchange aborts.
(The tests caught my own first draft verifying one party's signature with the *other* party's pinned key, a good reminder
that key-pinning bugs are easy to write.)

## 8.3 ElGamal encryption

Key: secret `x`, public `y = g^x`. Encrypt `m` with a **fresh** random `k`: `(c1, c2) = (g^k, m·y^k)`; decrypt
`m = c2 / c1^x`. It is Diffie-Hellman in disguise: `y^k` is the shared secret masking the message. The textbook example
(p = 2579, g = 2, x = 765, m = 1299, k = 853) gives `y = 949` and ciphertext **(435, 2396)**, which decrypts back to 1299.
Also tested over ffdhe2048 with a 22-byte message. Two properties demonstrated:

- **Malleable:** multiplying `c2` by 3 decrypts to `3m` (mod p); an attacker edits the plaintext without the key.
- **Reusing `k` is catastrophic:** two ciphertexts under the same `k` satisfy `c2_a / c2_b = m_a / m_b`; knowing one
  message reveals the other (demo: knowing `m1 = 1000` recovers `m2 = 777`). The same mistake broke Sony's ECDSA signatures.

## 8.5 DH group sizes and performance

Python big-integer arithmetic, 30 runs each (`python -m cryptolab.ch08.bench_dh_groups`):

| Group | Size (bits) | Security (bits) | Keygen ms | Shared-secret ms | Per-side handshake ms | Public value (bytes) | Cost vs X25519 |
|---|---:|---:|---:|---:|---:|---:|---:|
| ffdhe2048 | 2048 | 112 | 21.7 | 54.9 | 76.6 | 256 | 1,191x |
| ffdhe3072 | 3072 | 128 | 70.2 | 162.4 | 232.6 | 384 | 3,619x |
| ffdhe4096 | 4096 | 152 | 163.2 | 390.7 | 553.9 | 512 | 8,617x |
| X25519 (ECDH) | 255 | 128 | 0.032 | 0.032 | 0.064 | 32 | 1x |

Security levels are the NIST SP 800-57 estimates for finite-field DH. Absolute times are Python's (OpenSSL is several times
faster and real deployments use short ~2×security-bit exponents, cutting cost further), but the *ratios* are what matter.

**Recommendation.** Cost grows roughly with the cube of the modulus size: 128-bit security costs ~3x the 112-bit group, and
152-bit costs ~7x. **For new designs use X25519**: the same 128-bit security for a thousandth of the cost and 32-byte public
values. If you must use finite-field DH (legacy compatibility), use **ffdhe3072 or larger from the RFC 7919 list**, ephemeral
keys only, validate peer values, and never support 512- or 1,024-bit or non-standard groups (the Logjam attack exploited
exactly that). Note the `cryptography` library itself now flags FFDH as deprecated.

## 8.6 Authenticated key exchange for a chat app

**Threat model.** *Assets:* message contents, who is talking to whom. *Attackers:* an active network attacker (can drop,
modify, replay, inject); an untrusted relay server; a later thief of long-term keys or a device backup. *Goals:* mutual
authentication, no MITM (8.2), **forward secrecy**, replay/reorder protection. *Out of scope:* compromised endpoints, metadata.

**Design** (`ake.py`): long-term **Ed25519 identity** per user; per session an **ephemeral X25519** exchange.

```
1. A -> B : A_eph, A_id
2. B -> A : B_eph, B_id, Sig_B(T), MAC_B         T = H("AKE1" | A_eph | A_id | B_eph | B_id)
3. A -> B : Sig_A(T), MAC_A                      session keys = HKDF(X25519(A_eph, B_eph), salt = T)
```

| Property | How |
|---|---|
| No MITM | Both signatures cover **both ephemerals and both identities**; a substituted ephemeral changes T, so signatures fail. |
| No splicing/identity misbinding | Identities are inside T, so a signature cannot be reused in another session or for another pair. |
| Key confirmation | MACs under a key derived from the shared secret prove both sides derived the *same* keys. |
| Forward secrecy | Ephemeral secrets are deleted after the handshake (tested); stealing identity keys later reveals no past session. |
| Trust in identities | Trust-on-first-use plus a **safety number** (hash of the identity key) read out over a call; a changed key raises `IdentityChanged` until accepted after verification. |
| Replay / reorder / tamper | Per-direction AES-GCM keys, strictly increasing 64-bit counters in the nonce (direction-separated), transcript hash as AAD; a rejected message does not advance state. |

Tested: honest session both ways; replayed, reordered, and bit-flipped messages rejected; an impersonator presenting a
different identity under the same name is stopped by the pinned key; a MITM substituting its ephemeral key fails signature
verification; no ephemeral secret survives the handshake. **Limits:** TOFU is only as good as the first contact (hence the
safety-number check); no ratcheting (so compromise of a session key exposes that whole session, unlike Signal's double
ratchet); no deniability (signatures are non-repudiable, a deliberate trade-off here); this is a teaching protocol.
Use a vetted design (Noise, Signal, TLS 1.3, MLS) in production.
