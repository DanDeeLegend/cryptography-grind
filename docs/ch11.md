## 11.1 Avalanche effect

Flip one random input bit (64-byte messages, 2,000 trials each) and count how many output bits change. Ideal: 50%.

| Hash | Mean bits flipped | Min | Max |
|---|---|---|---|
| SHA-256 | 49.9% | 37.9% | 62.5% |
| SHA-1 | 49.9% | 35.6% | 62.5% |
| MD5 | 49.9% | 35.2% | 66.4% |
| CRC32 | 49.0% | 31.2% | 75.0% |
| byte-sum | 6.4% | 3.1% | 43.8% |

**Lesson: avalanche is necessary, not sufficient.** CRC32 looks fine here but is *linear* (`crc(a⊕b⊕c) = crc(a)⊕crc(b)⊕crc(c)`
for equal lengths; a test proves it), so an attacker can steer it. MD5 and SHA-1 also show perfect avalanche and are still
broken by collision attacks. Avalanche only catches lazy designs like the byte sum.

## 11.2 Birthday collisions on a truncated SHA-256

For a k-bit hash, a collision is expected after about 2^(k/2) evaluations, not 2^k. Mean over 20 runs per size:

| Hash bits | 2^(k/2) | Table method (evals) | Floyd cycle method (evals) |
|---|---|---|---|
| 16 | 256 | 275 | 1,437 |
| 20 | 1,024 | 1,252 | 4,442 |
| 24 | 4,096 | 5,021 | 24,745 |
| 28 | 16,384 | 21,253 | 43,402 |
| 32 | 65,536 | 80,637 | 173,046 |

The table method stores every hash (memory ≈ 2^(k/2)). The Floyd variant treats `x → H(x)` as a walk, finds the cycle with two
pointers and recovers the colliding pair from the cycle entry, using O(1) memory at the cost of roughly 2-6x more evaluations
(I count 3 per step; with 20 runs the Floyd column is noisy, so read it as "a small constant factor", not an exact ratio).
**Why it matters:** a 64-bit hash gives only ~2^32 collision security, which is why digests are 256 bits.

## 11.4 Password storage: naive SHA-256 vs Argon2id

Naive storage is `SHA-256(password)`: unsalted, so equal passwords give equal hashes (a test shows it), and designed to be fast.
Argon2id (19 MiB, t=2, p=1) uses a random per-hash salt, which is embedded in the stored string, and is memory-hard.
Measured on **one CPU thread**:

SHA-256: 1,648,822 guesses/s · Argon2id: 44 guesses/s (about 37,000x slower per guess)

| Search space | Naive SHA-256 | Argon2id |
|---|---|---|
| 100,000-word list | 0.06 s | 37.5 min |
| 8 chars, a-z0-9 (36^8) | 19.8 days | 2,008.9 years |
| 8 chars, all printable (95^8) | 127.5 years | 4,724,162.9 years |

**Caveats.** Single thread, no GPU: attackers with GPUs reach billions of fast-hash guesses per second, and GPUs are
less effective against memory-hard hashes but not powerless, so these absolute times are optimistic for the defender. Real
passwords follow patterns, so the wordlist row is the realistic one, and a long unique passphrase matters more than any hash.
Also use a server-side pepper if you can, rate-limit logins, and re-hash when parameters are raised.

## 11.6 File-integrity tool

`integrity.py build DIR` writes a manifest of SHA-256 digests; `verify DIR` reports `modified`, `missing` and `added` files and
exits non-zero on any difference. The tests cover all three cases.

A hash manifest only detects *accidents*: an attacker who edits a file can just regenerate the manifest. Pass `--key-file` and
the manifest carries an **HMAC-SHA256** tag over its contents, which cannot be recomputed without the key (the tests show a
regenerated manifest passing without a key and failing with one). Keep the key outside the directory being protected; digests
are compared with `hmac.compare_digest`.
