## 6.2 Modular exponentiation (square-and-multiply)

Public-key cryptography is built on `a^e mod n` with huge `e`. Multiplying `a` by itself `e` times is impossible for a
2,048-bit exponent, so walk the **bits** of `e` from the top: square the running result for every bit, and multiply by `a`
when the bit is 1. By hand, **7^13 mod 11**, with 13 = `1101` in binary:

| bit | square | then multiply by 7 if bit = 1 |
|---:|---:|---:|
| 1 | 1 | 7 |
| 1 | 5 (7² = 49) | 2 (5·7 = 35) |
| 0 | 4 (2² = 4) | 4 |
| 1 | 5 (4² = 16) | **2** (5·7 = 35) |

Result **2**, matching Python's `pow(7, 13, 11)`; 7 multiplications instead of 12. Each step reduces mod 11, so numbers never
grow. The script prints the same trace for any inputs and the tests compare it with `pow` on 300 random 100-bit cases.
Cost is `bits(e) + popcount(e)` modular multiplications: 19 for `e = 65537`, roughly 3,000 for a 2,048-bit private exponent.

## 6.4 Symmetric vs public-key speed

Same machine, AES-256-GCM on 1 MiB versus RSA-OAEP (SHA-256). RSA encrypts only a small block per operation, so throughput
is *bytes per operation × operations per second* (`python -m cryptolab.ch06.bench_sym_vs_pk`):

AES-256-GCM: **8,799 MB/s**

| RSA key | bytes per op | encrypt ops/s | decrypt ops/s | encrypt MB/s | decrypt MB/s | AES / RSA-decrypt |
|---:|---:|---:|---:|---:|---:|---:|
| 2048 | 190 | 29,579 | 2,957 | 5.62 | 0.562 | 15,660x |
| 3072 | 318 | 18,557 | 1,053 | 5.90 | 0.335 | 26,274x |
| 4096 | 446 | 11,074 | 556 | 4.94 | 0.248 | 35,484x |

**Why such a gap.** An AES block is 10 rounds of byte-level operations on 16 bytes, and CPUs have an instruction (AES-NI)
for the round; GCM's authenticator also has a carry-less-multiply instruction. One RSA private operation is a modular
exponentiation: ~2,000 squarings of 2,048-bit numbers, each costing on the order of (2048/64)² = 1,000 word multiplications.
That is millions of operations to move 190 bytes. Encryption is far faster than decryption because the public exponent
(65537) has 17 bits while the private exponent has ~2,048. The gap **widens with key size**: security margin is paid for in
cubic-ish cost. Hence the rule: **use public-key crypto only to agree on or protect a short key, and let a symmetric cipher
handle the data.**

## 6.5 A toy hybrid-encryption scheme

```
sender                                                    receiver
------                                                    --------
K  = random 256-bit AES key
ct = AES-256-GCM(K, message)          ---- blob ---->     K   = RSA-OAEP-decrypt(wrapped_key, private key)
wrapped_key = RSA-OAEP(public key, K)                     msg = AES-256-GCM-decrypt(K, ct)
blob = "HYB1" | len | wrapped_key | nonce | ct+tag
```

A fresh key per message makes a random 96-bit nonce safe. The wrapped key is bound into the GCM **associated data**, so a
ciphertext cannot be moved onto a different wrapped key, and an optional context (e.g. `user-7`) is bound too. All failures
(wrong recipient key, any flipped bit, truncation, wrong context) raise one generic error, giving an attacker no oracle.
A 1.32 MB message round-trips with **418 bytes of overhead**, versus RSA alone, which could carry 190 bytes per operation
and be slower by four orders of magnitude. This is the "envelope" pattern of TLS (before key agreement took over), PGP and
S/MIME.

## 6.6 Man-in-the-middle on an unauthenticated exchange

`mitm_sim.py` runs an ephemeral X25519 exchange where the network is attacker-controlled.

**Vulnerable.** The exchange never says *whose* key it is carrying. Mallory replaces each side's public key with her own,
shares one secret with Alice and a different one with Bob, and sits between them:

```
Alice <--key exchange--> Mallory <--key exchange--> Bob
  (secret K1 with Mallory)          (secret K2 with Mallory)
```

Everything encrypts and decrypts without error, so **neither side can tell**. The demo: Alice sends `meet at noon`;
Mallory decrypts it, edits it, re-encrypts it under Bob's key, and **Bob reads `meet at midnight`** with a valid tag.
Encryption provided zero protection, because it protected the channel to the *wrong party*.

**Fixed (detectable).** Each side hashes the two public keys it saw into a short code and the humans compare it over a
channel Mallory does not control (a call, in person). Honest run: both show `68B1-6D3A-BABA`. Under attack: Alice sees
`2A96-E602-9437`, Bob sees `7DF9-5E50-FA1A`, **mismatch, attack detected**. This is how Signal's "safety numbers" and
ZRTP's short authentication strings work. Its weakness is human: if nobody compares, nothing is detected. Chapter 8.2 closes
the gap with digital signatures so the check is automatic.
