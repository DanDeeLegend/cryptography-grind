## 4.1 One AES round, traced (FIPS-197 Appendix B)

Plaintext `3243f6a8885a308d313198a2e0370734`, key `2b7e151628aed2a6abf7158809cf4f3c`. The state is a 4×4 byte matrix filled
column by column. Every value below is produced by the step-by-step implementation in `aes.py` (no library call) and the tests
assert each against the FIPS-197 document:

| Step | State (hex) |
|---|---|
| input | `3243f6a8885a308d313198a2e0370734` |
| round 0: AddRoundKey (plaintext ⊕ key) | `193de3bea0f4e22b9ac68d2ae9f84808` |
| round 1: SubBytes | `d42711aee0bf98f1b8b45de51e415230` |
| round 1: ShiftRows | `d4bf5d30e0b452aeb84111f11e2798e5` |
| round 1: MixColumns | `046681e5e0cb199a48f8d37a2806264c` |
| round-1 key | `a0fafe1788542cb123a339392a6c7605` |
| round 1: AddRoundKey | `a49c7ff2689f352b6b5bea43026a5049` |

What each step is for: **SubBytes** (byte → S-box) is the only non-linear step; the S-box is the multiplicative inverse in
GF(2^8) followed by an affine map (computed in the code, not typed in). **ShiftRows** rotates row *r* left by *r* so bytes
leave their column. **MixColumns** multiplies each column by a fixed matrix over GF(2^8) so every output byte depends on four
inputs. Together ShiftRows + MixColumns give *diffusion* (two rounds spread one flipped bit across the block); SubBytes gives
*confusion*. **AddRoundKey** is the only step that uses the key. The final round skips MixColumns.

## 4.4 AES-NI vs software AES

CBC mode, best of 5, x86-64 sandbox with the AES-NI CPU flag:

| Data size | AES-NI (PyCryptodome) MB/s | AES-NI (OpenSSL) MB/s | Software C, AES-NI off MB/s | AES-NI / software |
|---:|---:|---:|---:|---:|
| 64 KiB | 802 | 1,410 | 235 | 3.4x |
| 1,024 KiB | 841 | 742 | 251 | 3.4x |
| 16,384 KiB | 845 | 656 | 246 | 3.4x |

Pure-Python AES (this repo, 4 KiB): **0.188 MB/s**, about **1,300x slower** than software C.

**Reading it.** Hardware acceleration buys roughly **3-4x** over good software AES here (more on CPUs where a single core
can issue AES instructions back-to-back and for parallelisable modes like CTR/GCM), and a well-written C implementation is
itself ~1,300x faster than naive Python. Besides speed, AES-NI executes in constant time with no table lookups, which also
removes the cache-timing side channels that table-based software AES (and `aes.py`) are exposed to. The OpenSSL numbers move
around more than the others with data size (cache and frequency effects), so treat single figures as ballpark.

## 4.5 File-encryption utility (AES-256-GCM)

```bash
python -m cryptolab.ch04.filecrypt encrypt report.pdf report.pdf.enc      # prompts for a password
python -m cryptolab.ch04.filecrypt decrypt report.pdf.enc report.pdf
```

Design decisions, each a classic mistake avoided: scrypt turns the password into a 32-byte key with a random salt; AES-GCM
comes from the `cryptography` package (never hand-roll the cipher); the nonce is 8 random bytes per file plus a 4-byte chunk
counter so no (key, nonce) pair repeats; files are encrypted in 64 KiB authenticated chunks; the header and a "last chunk"
flag are authenticated data, so **truncating, appending or reordering chunks is detected**, not just flipped bits; and
decryption writes to a temp file renamed into place only after every chunk verified, so unverified plaintext is never
left behind.

Tests (all pass): round-trips for sizes 0, 1, 100, 65,535, 65,536, 65,537 and 200,000 bytes and a text file; two
encryptions of the same file differ; tamper tests for a flipped body bit, a flipped header bit, truncation, appended data,
chunk reordering, a wrong password and a junk file. Each failure raises `TamperError` and leaves no output file.
