## 12.1 HMAC-SHA256 from scratch

`HMAC(K, m) = H((K⊕opad) ‖ H((K⊕ipad) ‖ m))`, with keys longer than the 64-byte block hashed first. It sits on top of my own
SHA-256 (FIPS 180-4), which is checked against `hashlib` for every length 0-199 plus 1,000 and 4,096 bytes (all padding
boundaries). HMAC passes **RFC 4231 test cases 1, 2, 3, 4, 6 and 7** (case 5 only tests truncation) and equals Python's `hmac` output.

## 12.2 Length-extension attack on `SHA256(secret ‖ message)`

A Merkle-Damgård hash outputs its internal state. So from `tag = SHA256(secret ‖ msg)` an attacker can load that state, hash
more data and get the valid tag of `msg ‖ padding ‖ suffix` without the secret. The only unknown, the secret's length, is
found by trying 1..64 and asking the verifier.

```
forged_message: b'user=guest&amount=100\x80\x00...\x01\x98&admin=true'
accepted: True   guessed_secret_len: 30 (true: 30)   hmac_resists: True
```

The forged message contains the glue padding, which a parser that reads `key=value` pairs will happily skip over, and
`admin=true` is appended. **HMAC resists** because the visible tag is the output of an *outer* hash over a fresh keyed block;
resuming from it extends nothing the verifier checks (the same procedure fails all 64 length guesses). SHA-3 and SHA-512/256 are
immune by design, but still use HMAC or KMAC rather than `H(key ‖ m)`.

## 12.4 MAC-then-encrypt vs encrypt-then-MAC (with a working padding oracle)

| | MtE | EtM |
|---|---|---|
| Order | tag the plaintext, then CBC-encrypt `plaintext ‖ tag ‖ padding` | CBC-encrypt, then tag `iv ‖ ciphertext` |
| First check on receipt | decrypt and unpad (on attacker-controlled bytes) | verify the tag, reject everything modified |
| Error signals | "bad padding" vs "bad MAC" can differ | one `Invalid` for everything |

**Demo.** A server that answers "bad padding" differently from "bad MAC" is an oracle. Vaudenay's attack recovers each block's
intermediate value one byte at a time (with a second query to rule out the accidental `02 02` padding case). Against MtE it
recovered the whole secret `session=9f8e7d6c5b4a; user=daniel` with **10,182 queries** for five blocks, with no key. Run
against EtM with the same forged inputs, the attack finds no signal at all (every attempt is rejected identically), and the
tests also flip bits in the ciphertext, IV and tag to confirm each is refused.

**Lucky 13 (2013)** showed that even with *identical* error messages, MtE leaks through the timing difference between the
padding-failed and MAC-failed paths; this is described, not reproduced here. SSL/TLS used MtE for CBC suites, which is part of why TLS 1.3
removed CBC. Professional rule: use an AEAD (GCM, ChaCha20-Poly1305); if you must compose, do EtM.

## 12.5 Signed webhooks with replay protection

Header `t=<unix>,id=<unique>,v1=<HMAC-SHA256 of "t.id." ‖ raw body>`. The receiver: parses, checks the timestamp is within 5
minutes, verifies the MAC with `compare_digest` against any active secret (**key rotation**), and only then records the id.
Tested: valid event accepted; replay, tampered body, wrong secret, stale timestamp, malformed header and swapped id/timestamp
rejected; an unauthenticated forged request does *not* consume the real id; expired ids are purged so memory stays bounded.

**Limits.** The replay cache here is in-process. Across several server instances use a shared store (Redis `SET NX` with a
TTL). Sign the **raw** request body: re-serialising parsed JSON changes bytes and breaks the MAC.

## 12.6 Encrypt-then-MAC vs AES-GCM throughput

AES-128-CBC + HMAC-SHA256 (EtM) vs AES-128-GCM, encrypt + decrypt per message, single thread:

| Message size | AES-CBC + HMAC (MB/s) | AES-GCM (MB/s) | GCM speed-up |
|---|---|---|---|
| 64 B | 4 | 57 | 16.2x |
| 1 KiB | 47 | 732 | 15.6x |
| 64 KiB | 390 | 5,608 | 14.4x |
| 1024 KiB | 257 | 1,165 | 4.5x |

GCM is faster mainly because it is one pass through hardware-accelerated AES and carry-less multiplication, whereas CBC
encryption cannot be parallelised and the HMAC is a second pass; small-message gaps also include the Python wrapper (padding,
two key handles). The 1 MiB row for both columns drops, likely from cache effects, and I did not repeat the run to check the noise,
so don't read that row's ratio precisely. GCM's real cost is operational: **never reuse a nonce under one key** (chapter 5).
