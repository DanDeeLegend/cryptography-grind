## 13.2 Certificate path validation

`chain_validate.validate(chain, anchors, hostname)` makes every step of RFC 5280 path validation visible:

1. leaf **SAN** matches the hostname (a wildcard covers exactly one label; CN is not consulted);
2. each certificate is inside its **validity window**;
3. each certificate's **signature verifies** under its issuer's key and the issuer *name* matches;
4. each issuer is a **CA** (`basicConstraints`) with `keyCertSign`, and respects **`pathLenConstraint`**;
5. the path ends at a **trust anchor**, matched by *subject and public key*.

Point 5 matters: a real chain sends a root that is **cross-signed** (chapter 10 found GTS Root R1 signed by GlobalSign). It is a
different certificate from the self-signed root in the trust store but has the same key, so matching by fingerprint would
wrongly fail it, while matching by name alone would trust an impostor. Tests cover this with an impostor root that has the
right name and the wrong key.

**Tested against a local CA hierarchy (root → intermediate → leaf):** valid chain; chain that includes its root; wrong hostname;
wildcard rules; expired and not-yet-valid; untrusted root; missing intermediate; same-name impostor root; leaf signed by a
rogue intermediate with the genuine name; a non-CA certificate used as issuer; `pathLen=0` violation.

**Live run against the two sites I own**, using the system trust store (122 anchors loaded):

| Host | Result | Anchor | Revocation pointers on the leaf |
|---|---|---|---|
| ncf-website-ten.vercel.app | VALID | GTS Root R1 | CRL `c.pki.goog/wr1/…`, no OCSP |
| signalmap-8117.onrender.com | VALID | GTS Root R4 | CRL `c.pki.goog/we1/…`, no OCSP |

**Revocation (conceptual, not implemented).**

| Mechanism | How it works | Weakness |
|---|---|---|
| CRL | CA publishes a signed list of revoked serials | large, stale between publications |
| OCSP | client asks the CA "is serial X good?" | extra round trip, **leaks browsing to the CA**, most clients soft-fail |
| OCSP stapling | server attaches a fresh signed OCSP answer | server must support it; no must-staple, no guarantee |
| Short-lived certs | expire in days, so there is little to revoke | needs automated renewal (the direction the industry is moving) |

Both leaves here list only a CRL, with no OCSP URL, consistent with the move away from OCSP.

## 13.5 Capstone: a mini TLS handshake with an authenticated, encrypted channel

`mini_tls.py` is a TLS-1.3-*style* protocol, deliberately small enough to read in one sitting. **Not interoperable with TLS,
not for real use.**

```
Client                                              Server (leaf key + chain: leaf, intermediate)
  | ClientHello: random, X25519 pub, server name ------>|
  |                                                      | ECDH(shared), transcript starts
  |<-- ServerHello: random, X25519 pub                   |
  |<-- Certificate: [leaf, intermediate]                 |
  |<-- CertificateVerify: ECDSA over H(transcript so far)|   proves possession of the leaf key, bound to this exchange
  |<-- Finished: HMAC(finished_key, H(transcript))       |   proves the server derived the same keys
  | validate chain + hostname, verify signature, Finished|
  | Finished: HMAC over transcript incl. server Finished -->|
  |===== AES-128-GCM records (per-direction keys) =====>|
```

**Design decisions and what each prevents**

| Decision | Prevents |
|---|---|
| Ephemeral X25519 on both sides | past sessions can't be decrypted if the server's long-term key later leaks (forward secrecy) |
| Server signs the **transcript hash** | a recorded signature can't be replayed; swapping either side's ephemeral key (the chapter 6/8 MITM) breaks verification |
| Keys derived by HKDF with the transcript hash as context | keys are bound to this exact handshake |
| Finished MACs over the whole transcript | any modified, dropped or reordered handshake message |
| Separate keys per direction, nonce = IV ⊕ sequence number | reflection of a record back at its sender; nonce reuse |
| Sequence number implicit, used in the nonce | replay, reordering and deletion all fail authentication |
| Record type inside the ciphertext, `close_notify` record | truncation is detectable (`finish()` raises if EOF arrives without it) |
| One fixed suite, no negotiation | downgrade attacks (there is nothing to downgrade) |

**What the tests prove** (18 in this chapter): HKDF against RFC 5869 case 1; round trips in both directions; plaintext absent from
the wire; two sessions never share keys; wrong hostname and untrusted CA rejected; an attacker holding the genuine public chain
but not the private key is caught by CertificateVerify; swapping an ephemeral key in either hello is caught; **flipping one
byte at any sampled position of the server's flight is detected**; record tampering, replay, reordering, reflection and
truncation are all rejected.

**Known gaps (honest list).** No client authentication, session resumption or 0-RTT; no certificate-revocation check; no EKU or name
constraints in validation; one cipher suite; no key update, so a long-lived connection reuses keys; the sequence counter would
overflow after 2^64 records; hand-rolled HKDF/framing is educational (use a TLS library in practice); Python is not
constant-time everywhere and nothing here has been reviewed for side channels.
