## 7.1 A tiny RSA key pair, every value

`python -m cryptolab.ch07.rsa_toy` prints the full derivation for p = 61, q = 53:

| Step | Value |
|---|---|
| n = p·q | 61 · 53 = **3233** |
| φ(n) = (p−1)(q−1) | 60 · 52 = **3120** |
| e (coprime to φ) | **17**, gcd(17, 3120) = 1 |
| d = e⁻¹ mod φ (extended Euclid) | **2753**, check: 17 · 2753 = 46801 = 1 + 15 · 3120 |
| public key / private key | (3233, 17) / 2753 |
| encrypt m = 65 | 65¹⁷ mod 3233 = **2790** |
| decrypt | 2790²⁷⁵³ mod 3233 = **65** |

It works because `e·d = 1 + k·φ(n)`, so `m^(ed) = m · (m^φ)^k = m (mod n)` by Euler's theorem. The tests decrypt **every
one of the 3,233 possible messages**, not just 65. Security rests on one fact: computing `d` needs φ(n), which needs the
factors of n, and factoring a 2,048-bit n is infeasible.

## 7.2 RSA with proper padding

`rsa_oaep.py` implements **RSAES-OAEP** (RFC 8017, SHA-256, MGF1) from scratch on the raw RSA operation, and checks it
against a reference library **in both directions**: our padding decrypted by the library, and library ciphertexts decrypted
by ours, over ten messages of different lengths. (Honest note on "known test vectors": this checks interoperability with the
reference implementation instead of hard-coding published vectors, which I did not want to reproduce from memory;
the stronger evidence is that two independent implementations agree.) Tests also cover label binding, randomised
ciphertexts, the 190-byte message limit for a 2,048-bit key, and **one uniform error for every failure** (telling padding
errors apart enables Manger's chosen-ciphertext attack).

**Why not "textbook" RSA?** Three concrete breaks, all demonstrated (`python -m cryptolab.ch07.rsa_oaep`):

1. **Deterministic**: the same message always gives the same ciphertext, so an eavesdropper can confirm guesses.
2. **Malleable**: `c1 · c2 mod n` decrypts to `m1 · m2`; an attacker edits plaintexts (e.g. multiplies an amount) without
   the key. Demo: 6 × 7 → 42.
3. **Small message, small e**: with e = 3 and `m^3 < n` there is no modular reduction, so an ordinary integer cube root
   of the ciphertext recovers the plaintext with no private key. Demo recovers `b'attack at dawn'`.

OAEP fixes all three: random seed (non-deterministic), a redundancy check (malleated ciphertexts fail to decode) and
full-width padding (the integer is always huge).

## 7.4 Square-and-multiply vs naive exponentiation

2,048-bit modulus; one modular multiplication costs 12.5 µs here (Python big integers):

| Exponent bits | exponent | naive mults | naive time | square-and-multiply | speed-up |
|---:|---:|---:|---:|---:|---:|
| 8 | 175 | 175 | 2.4 ms | 175 µs | 14x |
| 12 | 2,225 | 2,225 | 26.9 ms | 159 µs | 170x |
| 16 | 47,151 | 47,151 | 673.0 ms | 349 µs | 1,931x |
| **17** | **65,537 (the usual e)** | 65,537 | 908.2 ms | 178 µs | **5,100x** |
| 20 | 872,289 | 872,289 | 12,055.7 ms | 337 µs | 35,730x |
| 22 | 3,163,399 | 3,163,399 | 39,622.0 ms | 330 µs | 120,018x |

With a **2,048-bit private exponent**, square-and-multiply takes **34.5 ms**. The naive method would need about 2^2047
multiplications, roughly **10^604 years**. Naive cost grows *linearly in the exponent's value* (so exponentially in its
bit length); square-and-multiply grows linearly in the bit length. The speed-up grows with the exponent, which is
why RSA is usable at all. (The square-and-multiply column is noisy at the microsecond scale; the trend is what matters.)

## 7.6 Common-factor key break

If two RSA moduli share a prime, `gcd(n1, n2)` returns it, and both keys fall to a gcd computation: no factoring needed
(`python -m cryptolab.ch07.common_factor`):

```
two 128-bit moduli sharing a prime: gcd(n1, n2) = 17945745536513560063  (== p: True)
  n1 = 17945745536513560063 * 10308950108773528939; n2 = 17945745536513560063 * 9638451904978136567
  intercepted ciphertext for n1 decrypts to 123456789
fleet of 600 devices: 327 keys share a prime (55%); pairwise 93 ms vs batch GCD 16 ms; same set: True
```

At scale, comparing all pairs is O(n²); **batch GCD** (Bernstein) builds a product tree of all moduli and a remainder tree,
computing `gcd(n_i, product of all others)` for every key in quasi-linear time (the toy fleet already shows ~6x). A subtle
case the tests caught: if *both* primes of a key appear in other keys, that gcd equals n itself, so the code must split it
by gcd-ing against individual moduli.

**The real-world finding.** In 2012, two independent research groups (Heninger, Durumeric, Wustrow & Halderman, *Mining
Your Ps and Qs*, USENIX Security; and Lenstra et al., *Ron was wrong, Whit is right*) collected public keys from the
internet and ran exactly this computation. A measurable fraction of RSA keys, on the order of a few tenths of a percent to
about half a percent of hosts (figures quoted from memory; check the papers before citing exact numbers), shared a prime with
another key and could be factored outright. The cause was not weak RSA but a weak random-number generator: embedded
devices (routers, firewalls) generated their keys at **first boot, before the OS had gathered entropy**, so many devices drew
the same primes. **Lessons:** RSA key generation is only as good as the randomness beneath it; generate keys after entropy
is available (`getrandom()` blocking semantics), and monitoring a fleet's public keys for shared factors is cheap.
