## 2.1 One-time pad and the two-time-pad break

**OTP**: `ciphertext = plaintext XOR key`, with a truly random key as long as the message, used **once**. It is perfectly
secret: for *any* plaintext of the same length there is a key that yields the observed ciphertext (`key = ciphertext XOR
plaintext`), so the ciphertext carries no information. The demo "decrypts" one ciphertext into two different messages.

**Reuse the key and the proof collapses.** `c1 XOR c2 = (p1 XOR k) XOR (p2 XOR k) = p1 XOR p2`: the key cancels and the
attacker holds the XOR of two plaintexts. Because both are language, sliding a guessed word (a "crib") along that XOR reveals
the other message wherever the guess is right (`DAWN `, `LLS B`, ... in the demo).

**Takeaway.** The one-time pad is unbreakable but impractical (key as long as the data, never reused). Every real stream
cipher is a *generator* that stretches a short key into a long keystream, and the nonce rule ("never reuse key + nonce") is
the OTP rule in disguise.

## 2.2 LFSR stream cipher and state recovery

A linear-feedback shift register (here 16 bits, recurrence `s[n] = s[n-16] ⊕ s[n-14] ⊕ s[n-13] ⊕ s[n-11]`) is a cheap,
fast keystream source with maximal period 2^16 - 1 (checked in the tests). It is also **linear**, and linear is the problem.

**Attack.** Known plaintext gives keystream (`keystream = ciphertext XOR plaintext`). The Berlekamp–Massey algorithm finds
the shortest LFSR that generates any observed bit sequence, needing only **2L bits** for an L-bit register. With just **6
known bytes (48 bits)** it recovered L = 16 and the taps `[11, 13, 14, 16]`, so the whole keystream and the rest of the
message followed. Recovered state: the first 16 keystream bits are the register's initial contents; the recurrence predicts
every later bit.

**Takeaway.** Linearity means 2L known bits break the cipher however large the period is. Real designs (A5/1, Trivium,
Grain, ChaCha) add non-linear mixing for exactly this reason.

## 2.4 Keystream-reuse detector

Two ciphertexts from the same key *and nonce* (ChaCha20 with a repeated nonce in the sample) XOR to the XOR of their
plaintexts. **Detection:** ASCII text XOR ASCII text never sets the top bit of a byte, so reused-keystream pairs score
**1.00** on "fraction of XOR bytes below 0x80", versus **0.44** for independent keystreams (random bytes give ~0.5).

**Recovery:** the tool slides common words along the XOR and keeps hits whose revealed text looks like English (character
bigram plausibility). On the sample it surfaces true fragments in *both* messages, e.g. crib `" will "` ↔ `"the st"`, crib
`" and "` ↔ `"day a"`. Honest limits: on short messages some false hits are unavoidable, which is why the tool ranks
candidates and the confidence thresholds are heuristics calibrated on the sample; the *which message holds the crib* step is
a human judgement, extended by guessing the next word. This is exactly how analysts attacked reused pads in practice.

**Takeaway.** Nonce reuse in any stream-cipher mode (including AES-CTR/GCM) is catastrophic. The defence is engineering:
random 96-bit nonces with a bound on messages per key, or counters, or a misuse-resistant mode like AES-GCM-SIV.
