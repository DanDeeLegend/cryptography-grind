## 10.1 RSA signatures with PKCS#1 v1.5 padding, from scratch

Signing: hash the message, wrap the hash as a DER `DigestInfo`, pad it to the modulus length as
`00 01 FF…FF 00 ‖ DigestInfo`, then apply the private exponent. PKCS#1 v1.5 signing is deterministic, so the strongest
check available is **byte-for-byte equality with OpenSSL** for the same key and message, and the tests assert exactly that
(for empty, short and long messages), plus cross-verification in both directions.

```
byte_identical_to_openssl: True        tampered_message_rejected: True
ours_verifies: True                    tampered_signature_rejected: True
library_signature_verifies_in_ours: True   openssl_accepts_ours: True
```

**Verification design choice.** `verify` rebuilds the *expected* encoding and compares the whole block; it does not parse the
padding. Parsers that stop at the digest and ignore trailing bytes are what enabled Bleichenbacher's low-exponent forgery
(2006) in real TLS/X.509 libraries. A test builds a block with a valid digest but garbage after it and checks we reject it.
We also reject `s >= n` and wrong-length signatures.

*Professionals:* prefer RSA-PSS or Ed25519 for new systems; PKCS#1 v1.5 remains for compatibility (X.509, JWT RS256).

## 10.5 Forging textbook RSA signatures

If you sign `m^d mod n` with no hash and no padding, the multiplicative structure of RSA gives three forgeries, none using `d`:

| Attack | How | Result in the demo |
|---|---|---|
| Existential | pick random `s`, claim `m = s^e` | valid pair, attacker doesn't choose `m` |
| Product | `(m1·m2, s1·s2)` from two honest signatures | signature on `m1·m2` (143 = 11·13 in the test) |
| Blinding | ask the signer to sign `m·r^e`, divide the answer by `r` | signature on a message the signer refused to sign |

All three verify under the textbook verifier. Offered to the padded verifier from 10.1, a random signature is rejected
(`random_signature_accepted: False`): hashing destroys the algebraic structure the attacks depend on, and the fixed padding makes a
random integer overwhelmingly unlikely to decode to a valid block.

## 10.6 Inspecting real certificate chains

`cert_chain.py` fetches the chain a server sends (unverified, to look at it), then checks that each certificate's signature
validates under the next certificate's public key. Run against the two sites I own:

| Host | Leaf | Intermediate | Last cert sent |
|---|---|---|---|
| ncf-website-ten.vercel.app | `*.vercel.app`, RSA-2048, exp 2026-11-27 | WR1 (Google Trust Services) | GTS Root R1 (RSA-4096), **cross-signed by GlobalSign Root CA** |
| signalmap-8117.onrender.com | `onrender.com`, EC P-256, exp 2026-12-20 | WE1 (Google Trust Services) | GTS Root R4 (EC P-384), cross-signed by GlobalSign Root CA |

Every link verified (`signed by next cert: True`). Observations: both sites use Google Trust Services; the last certificate is
a *cross-signed* root, which lets older clients that only trust GlobalSign still build a path; and the leaf certificates are
short-lived (renewal is automated). This checks the **signatures only**; it is not full path validation (names, validity
dates, constraints, revocation), which is chapter 13.
